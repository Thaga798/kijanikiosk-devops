# Week 4 Tuesday Reflection

## Question 1: The State File as a System

Terraform knows about attributes that I did not explicitly declare because Terraform communicates with the infrastructure through a provider. The provider understands the resources it manages and returns information about those resources after Terraform creates or refreshes them. Terraform then records that information in the state file so that it can compare the real infrastructure with the desired configuration during future plans and applies.

The configuration file describes what I want Terraform to manage, while the state file records what Terraform knows about the resource it is managing, including provider-generated information and the resource's current identity. This is why the state can contain information that is not written directly in the Terraform configuration.

When `terraform destroy` is run successfully, Terraform destroys the managed infrastructure and removes the corresponding resources from the Terraform state. In my Tuesday work, the `null_resource.kijanikiosk_api` resource was removed from the state after the destroy operation, leaving the state with no managed resources.

If I manually deleted the state file without destroying the infrastructure, the actual infrastructure would still exist, but Terraform would lose its record of what it previously managed. On the next `terraform plan`, Terraform would no longer be able to match the existing infrastructure to its state. Depending on the resource and configuration, Terraform could propose creating resources again, which could result in duplicate infrastructure or other unexpected changes.

The correct recovery procedure is not to simply recreate resources blindly. The existing infrastructure should first be identified and the Terraform state should be recovered from a backup or remote backend if one is available. If the state cannot be recovered, existing resources should be imported into Terraform state using the appropriate import mechanism. The configuration should then be compared with the recovered/imported state before applying any changes.

## Question 2: The (known after apply) Values

Terraform uses a planning phase to calculate the changes it intends to make before actually creating or modifying infrastructure. Some values cannot be known during this phase because they are generated by the provider or by the infrastructure only when the resource is created.

One example from my Terraform work is the resource ID. The ID for the `null_resource.kijanikiosk_api` resource was not known when Terraform initially planned the creation. Terraform generates the resource ID as part of creating the resource, so the final ID can only be recorded after the apply operation completes.

A second example is an infrastructure-generated address or other provider-generated resource attribute. For a VM-based deployment, a private or public IP can be assigned by the infrastructure system when the VM is created rather than being known before creation. Terraform therefore represents such a value as `(known after apply)` during the plan when it cannot calculate it in advance.

The important point is that `(known after apply)` does not mean Terraform has failed to calculate the value. It means the value depends on an operation that has not happened yet.

If an output value depends on a `(known after apply)` attribute, Terraform also cannot display the final value during the plan. The output is shown as depending on a value that will become known after the apply. Once the resource has been created, Terraform records the actual value in state and the output can then display it.

## Question 3: Hardcoded vs Variable

Hardcoding a specific IP address in a security group or SSH ingress rule is a problem for a shared team configuration because the address may only be valid for one developer, network, or environment. Other team members may work from different networks, and the production environment may require completely different trusted source addresses. A hardcoded address therefore reduces reuse and can either block legitimate access or leave access configured for an address that should no longer be trusted.

The better approach is to make the trusted SSH source addresses a Terraform variable. The environment or deployment can then provide the appropriate values without changing the resource definition itself. This separates reusable infrastructure logic from environment-specific security settings.

For example, the security configuration could reference a variable representing the allowed SSH CIDR blocks, while staging and production provide different values. This makes the configuration easier to review, safer to reuse, and less likely to require direct edits to infrastructure code.

The appropriate Terraform type for a variable that accepts a list of IP addresses or CIDR blocks is `list(string)`. Each element is a string representing an address or CIDR range, for example a list containing one or more trusted SSH source networks.

## Question 4: What Tuesday's Configuration Cannot Do

For a production deployment, the values that would need to differ from staging include the deployment region, instance type, SSH key name, VPC or network, subnet or network range, security-group rules and trusted source addresses, VM count, VM names or roles, and other environment-specific settings such as IP allocation. The exact values depend on the production infrastructure requirements, but these are the types of values that should not be permanently tied to staging.

Tuesday's configuration was designed around a single environment and a single server/resource definition. If production required a larger instance type, a different VPC, and a different number of VMs, I would have to modify the configuration and variable values manually for the production deployment. That creates a risk of accidentally changing staging settings, duplicating configuration, or introducing differences between environments.

With the current one-configuration approach, changing the number of VMs is especially problematic because the configuration does not yet model multiple servers as a reusable collection. It would require adding or removing resource definitions or otherwise changing the configuration structure. A different VPC would also require changing the networking-related values and potentially the security configuration. A larger production instance would require a different instance-type value.

This is the limitation that Wednesday's work is intended to solve. A reusable module and environment-specific variables allow the infrastructure logic to remain the same while the values for staging and production are supplied separately. Using a collection such as `for_each` also allows the same module to create multiple server roles without copying the resource definition. This makes the infrastructure easier to scale, review, and reproduce across environments.
