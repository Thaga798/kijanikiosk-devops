# Week 4 Thursday Reflection

## Question 1: Ansible vs Bash Idempotency

Ansible achieves idempotency through its modules, which understand the desired state instead of blindly executing a command. In our KijaniKiosk playbook, `ansible.builtin.user` with `state: present` checks whether the requested user already exists and whether its relevant attributes match the desired configuration. If `kk-api` already exists in the required state, Ansible reports `ok` and does not make a change. If the user is missing, the module creates it and reports `changed`. If we used `ansible.builtin.shell: useradd kk-api`, Ansible would execute the command every time the task runs, even when the account already exists, potentially producing an error. The shell module is therefore generally unsuitable for provisioning tasks because Ansible cannot reliably infer the command's intended state or whether the command has already achieved it.

## Question 2: Handler Behaviour Under Parallel Execution

If the unit file template changes on host A and host B but is `ok` on host C, the Restart service handler runs once on host A and once on host B, for two handler executions across the three hosts. Handlers are evaluated per host, so a notification generated on one server does not trigger the handler on another server. If two different tasks on the same host both change and both notify the same handler, that handler still runs only once on that host during the play. Ansible queues handler notifications and deduplicates them until the handler execution point. This rule is important because several configuration tasks may update related files during one playbook run. Instead of restarting the service after every individual change, Ansible waits and performs one restart after all notified tasks have completed. This reduces unnecessary service interruptions and makes the playbook more efficient.

## Question 3: The Terraform to Ansible Inventory Bridge

One approach is to generate the Ansible inventory directly from Terraform state or Terraform outputs. For example, the `server_ips` output from our Terraform configuration can be consumed by a script that generates `inventory.ini`, keeping the inventory synchronized with the current infrastructure state. A second approach is dynamic inventory through a cloud provider API, where an Ansible inventory plugin queries the provider and discovers instances, addresses, tags, or groups automatically. The Terraform-state approach is simple and predictable for our current three Multipass servers, but it depends on local Terraform state/output access and requires an integration step. Cloud API discovery is more automatic and scales better, but it requires provider credentials, API access, and provider-specific configuration. For the three-engineer KijaniKiosk team, I would use Terraform outputs to generate inventory because the infrastructure is already managed by Terraform and the setup is smaller and easier to maintain.

## Question 4: Configuration Drift in the Ansible Model

Ansible handles drift primarily through reconciliation when the playbook is run; it is not a continuously running drift-detection system. If an engineer manually changes UFW rules on the payments server, the next run of a task using `community.general.ufw` or another appropriate firewall module compares the server's relevant state with the playbook's desired configuration. If the desired rule is missing or incorrect, Ansible changes it and reports `changed`. This differs from Terraform, where `terraform plan` refreshes managed resource state and can show detected differences before applying changes. Ansible normally does not provide the same separate, persistent plan-and-detect workflow for arbitrary host configuration. It also does not automatically run in the background to alert the team whenever someone changes a server. Operationally, KijaniKiosk engineers should run Ansible regularly or through CI/CD and keep configuration changes in the playbook, because manual changes can remain unnoticed until the next reconciliation run.
